# CONVENTIONS.md — how to work in this wake workspace

This file is copied into every workspace by `wake init`. It's written for
agents (including "dumb" ones without MCP access, working on raw files). If
MCP tools are available, prefer them — they enforce these rules for you. Raw
file edits are legal and the indexer will pick them up either way.

## File layout

```
projects/<slug>/project.md          # project node (authored)
projects/<slug>/status.md           # DERIVED — do not hand-edit
projects/<slug>/activity.ndjson     # project-level activity log
projects/<slug>/issues/<ulid>.md    # issue node (authored body, derived state)
projects/<slug>/issues/<ulid>.ndjson# per-issue activity log
docs/<path>.md                      # knowledge docs, any nesting under docs/
artifacts/<hash>.<ext>              # immutable content-addressed blob
artifacts/<hash>.md                 # artifact sidecar (frontmatter + caption)
activity/log.ndjson                 # workspace-level activity (docs, artifacts)
.wake/                              # SQLite index — NEVER hand-edit, safe to delete
CONVENTIONS.md                      # this file
```

## Files are ground truth

Markdown + YAML frontmatter for nodes, NDJSON for activity logs, plain blobs
for artifacts. `.wake/index.db` is a disposable SQLite cache rebuilt from
these files on open (full reindex if stale/missing, incremental catch-up
otherwise). **Never edit anything under `.wake/`.** If the index ever looks
wrong, delete `.wake/` and reopen the workspace — that must always be safe.

## Frontmatter fields

All node types share these base fields:

| field | required | notes |
|---|---|---|
| `id` | yes | ULID, read-only after creation |
| `type` | yes | `project` \| `issue` \| `doc` \| `artifact` |
| `title` | yes | plain text |
| `created` | yes | ISO timestamp, read-only after creation |
| `updated` | yes | ISO timestamp — **server-managed**, set on every write |
| `author` | no (default `unknown`) | human name or agent name |
| `tags` | no (default `[]`) | free-text array |
| `links` | no (default `[]`) | typed edges: `{to: <id>, type: <edge-type>}` |
| `space` | no (default `home`) | reserved for future multiplayer; leave alone |
| `archived` | no (default `false`) | soft removal — set via `archive_node`, not by hand |

Edge types for `links[]`: `relates-to`, `blocks`, `documents`, `discusses`,
`produced-by`. (`references` is index-only — produced by wiki-link
extraction, never written to frontmatter yourself.)

Per-type additional fields:

| type | field | required | notes |
|---|---|---|---|
| `issue` | `state` | yes | `triage \| todo \| in-progress \| blocked \| done \| dropped` — DERIVED, see below. The states are a **vocabulary, not an enforced workflow**: any transition between distinct states is legal by design (agents legitimately jump `triage → in-progress` or reopen `done`); your `reason` string is the audit trail. Issues may be created directly into any state. |
| `issue` | `project` | yes | id of the parent project |
| `artifact` | `file` | yes | blob filename under `artifacts/` |
| `artifact` | `mime` | no (default `application/octet-stream`) | e.g. `text/csv` |

## Derived — hands off

These are agent-owned exhaust, regenerated from activity. Never hand-edit:

- `projects/<slug>/status.md` — regenerated by `regenerate_status` only.
- an issue's `state` field — change it via `set_issue_state`, not by editing
  frontmatter directly.
- `updated` on any node — set automatically on every write.
- `*.ndjson` activity logs — append-only. You may append a well-formed event
  line; never edit or delete existing lines.
- `archived` on any node — toggle via `archive_node`.

## Nothing is deleted; archive instead

There is no delete over MCP, deliberately. `archive_node` is the cleanup verb:
soft and reversible, it hides a node from `list`, `search`, and status rollups
while keeping the file and its full history on disk. Don't hesitate to create
exploratory nodes — archiving them afterwards is cheap and honest. ("Remove
from view" and "destroy history" are different verbs; wake only has the first.)

MCP `update_node` hard-rejects patches touching any of these. If you're
editing files raw, the same restriction is a convention, not a technical
wall — respect it so status doesn't quietly go stale.

## Activity event shape (NDJSON, one JSON object per line)

```json
{"ts":"2026-07-20T14:00:00.000Z","actor":"claude-code","node":"01J...ULID","kind":"state_changed","payload":{"from":"todo","to":"in-progress","reason":"Starting implementation"}}
```

`kind` is one of: `created`, `state_changed`, `note`, `linked`, `doc_appended`,
`status_regenerated`, `field_updated`. `state_changed` payloads must be
`{from, to, reason}`. Issue and project activity live in their own
`.ndjson` file; doc and artifact `created` events (and anything else without
a more specific home) go to the workspace-level `activity/log.ndjson`.

## Wiki links

Write `[[Target]]` in any node body to reference another node by exact
**title** (case-insensitive) or by its **ULID**. The indexer extracts these
at index time and resolves them to backlinks — you don't need to know the
target's id, and a wiki link is never written back into frontmatter (that's
what `links[]` typed edges are for, when the relationship is structural
rather than prose-native).

## IDs and filenames

Every node gets a ULID (`id`). Issue files are named by their ULID:
`projects/<slug>/issues/<ulid>.md`. Project and doc paths are stable slugs
derived from the title instead — don't rename an existing project or doc
file casually, since paths are how the index recovers from a missing db.

## `space` field

Every node carries `space` (default `"home"`). It's indirection for a future
multiplayer model where a node's home space owns its writes and other spaces
hold read references. In v1 there is exactly one space. Leave this field
alone — don't set it to anything else.

## Prefer MCP tools; raw edits are legal

If the wake MCP server is available, use its tools (`create_node`,
`update_node`, `set_issue_state`, `log_activity`, `append_doc`/`write_doc`,
`link`, `regenerate_status`) — they validate frontmatter, enforce the
derived-field rules above, and write activity events for you. If MCP isn't
available, raw file edits are still legal: files are ground truth and the
indexer (watcher or `wake index`) picks up any well-formed change. Just
follow this document by hand — write valid frontmatter, append rather than
rewrite activity logs, and don't touch derived fields.

## When to open an issue vs. a note vs. a doc

- **Issue**: there is a discrete unit of work to track to completion —
  something with a state that should move through `triage → ... → done` (or
  `dropped`). If you're about to do multi-step work worth remembering, file
  it first.
- **Note** (`log_activity`): something worth recording on an existing node's
  timeline that isn't a state change — a decision, a run result, a link to a
  commit. Doesn't need its own issue.
- **Doc**: durable knowledge that isn't tied to one unit of work — an
  architecture writeup, a decision record, a reference. If you'd want to
  find it again by searching or browsing rather than by checking a task off,
  it's a doc.
